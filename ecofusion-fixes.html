Four defects found and fixed

A review of the platform's deployment path and revenue reporting turned up four problems — two that would have broken the live site, and two that were quietly reporting revenue figures that were not real. All four are fixed and awaiting review.

What was wrong

Would break the live site Fixed

Database changes never reached the live system

What was happening When the team added new features — sales, harvests, alerts, cameras — the matching changes to the database were not included in the automated release process. The instructions that create those tables existed on one developer's machine but were never added to the shared project.

Why it mattered Twenty-five parts of the application already depend on those tables. Anyone setting up a fresh copy of the system — a new environment, a new developer, a disaster recovery — would have got an application that builds successfully and then fails the moment someone opens Sales or Alerts. The current live database happens to be correct only because someone updated it by hand.

What we did Added the missing database instructions to the project and wired the release process to apply them automatically on every deployment, using the safe method that will not overwrite existing data. Also removed a duplicate, conflicting configuration file that was being silently ignored.

Broken feature Fixed

“Sign in with Google” could never have worked

What was happening Four configuration values the application needs at runtime were never registered with the hosting provider, including the two credentials required for Google sign-in. Clicking the Google button produced an error page from Google itself.

Why it mattered Beyond the login button, one of the missing values is the key used to encrypt the customer-system API credentials we store. Without it, the integrations settings page crashes rather than saving. A second missing value is used to verify that incoming messages from the CRM are genuine.

What we did Registered all four values in the deployment configuration and set up the Google credentials for local development, confirming the sign-in flow end to end. The actual secret values still need entering in the hosting dashboard — see step 2 below.

Wrong numbers shown Fixed

Every business unit reported the same invented revenue

What was happening The Business Units screen displayed $12,450 of month-to-date revenue on all seven cards. That figure was typed directly into the page during the build and never connected to the sales data. It never changed — not between units, not between users, not between months.

Why it mattered A brand-new account with no sales at all showed $87,150 of revenue across the seven units. This was found because a new user logged in and asked why their empty account already had figures in it — a good instinct, and the right question to ask.

What we did The screen now calculates each unit's real month-to-date revenue from completed sales, in a single database query, and shows $0 where there is none.

Accounting accuracy Fixed

Revenue was guessed from product names, and could vanish

What was happening Sales were never tagged with a business unit. Instead the system guessed, by looking for keywords in the product's name — a sale counted toward Aquaculture only if the product was named “fish”, “tilapia”, “catfish” or “seafood”.

Why it mattered Two failure modes, both silent. A product named for a keyword shared by two units — “energy” belonged to both Methane Gas and Solar — was counted in full toward each, so the seven units could total more than the business actually earned. And a correctly-sold product with an unrecognised name, say Nile Perch, counted toward nothing and simply disappeared from the dashboard, looking exactly like no sale at all.

What we did Sales staff can now choose the business unit directly when recording a sale. Where no choice is made, the old keyword matching still applies but assigns each sale to one unit only, and the overlapping keyword has been removed. Any revenue that matches nothing is now shown on screen as unassigned, so it can be corrected rather than lost.

Not fixed — recommended next

An administrator password is stored in the project files

The live administrator password sits in plain text in a file that is part of the shared codebase and its history. Anyone with access to the code has full administrative access to the platform. This should be moved into protected configuration and the password changed. Deleting it from the file alone does not remove it from the project history.

No limits on login attempts or account creation

Account registration is open to anyone who finds the web address, with no email confirmation and no cap on attempts. Protective code for this already exists in the project but is not connected to anything. Someone could create unlimited accounts or guess passwords without being slowed down.
